### 1.3 推導

**局長推導（E15）**

- **對齊紀錄的「v0.8.0 放置 300 秒 RED 1004（約 5 分鐘一局）」是誤讀**：300 秒是 V-D06 截圖前的**等待窗口**，不是局長。實際紀錄：驗收指南 §18 試玩步驟④「約 95 秒遊戲時間紅方到 1000」（7 塊）；v0.9.0 參考模型 `draw passive` 與 §1.3 性質 10「英雄完全不動時，紅方約在第 59 次計分到 1000」；v0.9.0 V9-C07 真實輸入劇本在開局 47.5 秒時比分 248／366（`vow-toolchain/v090-rage-result.json`）。所以**目前一局約 1～1.5 分鐘**，要到 12 分鐘需要慢約 8～14 倍，不是 2.4 倍。如果照「5 分鐘→12 分鐘」只慢 2.4 倍，實際局長只會變成 2.5～3.5 分鐘。
- 公式：一局長度 T ≈ 1000 ÷（每塊每秒分數 p × 領先方平均持有塊數 N̄）。p＝1/7 時 **T ≈ 7000 ÷ N̄ 秒**。

| 情境 | N̄（領先方平均持有塊數） | p＝2（v0.9.1） | p＝1/7（E15） | p＝1/8（Q8 替代） |

## 3. 實作順序與每步驗收

順序 `A → B → C → D`，每步一個可審查的提交（四步共用組裝根與場景，不並行寫檔）。開工前保存 `git status --short --branch` 與 `git rev-parse HEAD` 的輸出。任一步沒過，就回到該步的起點修，不在壞掉的基線上疊下一步。

**所有 V10 條文共同遵守**（承接 v0.9.0 §3）：
- 期望值一律寫成字面值，**不得讀 `CaptureTuning`／`CaptureBoardSpec`／`HexBoardLayout` 的欄位**來算期望值。
- 純邏輯時序一律用 dt＝0.25；**唯一例外**是 V10-A05 的 1.8 秒門檻組，用 dt＝1/64（E7）。
- PlayMode 一律固定 `Time.captureDeltaTime = 1/60`（V10-C04 固定 1/10），在 try/finally 或 TearDown 還原；窗口幀數寫死，**不得拉長 timeout、加 retry、加 sleep**。
- 「沒發生／相等」這類斷言都要附活性證據。
- 每條新測試都要先證明「錯誤實作會讓它紅」：純邏輯由 `mutation_check.py` 證明；Unity 測試由實作者把關鍵行改壞跑一次紅，寫進回報（附紅在哪個斷言），並用**改壞前的備份**還原。
- 時序條件先問「受測動作本身會不會重置計時」：`SeedScoresForTest` 清餘數；`SeedMatchElapsedForTest`／`SeedSiegeForTest` 只寫時鐘；傳送進光圈＝從 0 開始引導。
- 點擊前先斷言投影離畫面四邊都 ≥ 16px，不成立就判紅，不得換點。
- Unity 端只用 `ProfilerRecorder` 量配置。
- **線上（D 步）不使用任何按秒數重播的點擊劇本**（v0.9.0 修-10）；時間判斷只讀畫面上的倒數。

**指令**（`<U>`、`<P>`、`<T>` 同 v0.9.0 §3，前綴改為 `v0100-`）：`verify.sh`（`UNITY_REFS_DIR` 用絕對路徑）→ 場景有改時建場景 → EditMode → PlayMode（依序）；突變只在獨立 worktree 跑，不得與 Unity batchmode 同時跑（v0.9.0 修-9）。

## 5. 疑點（每題附建議）

- **Q1 規則集怎麼切？**（E1）建議**新增 `V0100Sanctuary`，保留 `V090Nineteen`／`V080Seven` 為夾具**：v0.8.0／v0.9.0 的純邏輯測試與既有突變全部逐字不改（§2.6 EditMode 0 條）。替代：直接改預設值（`ScorePerTilePerTick` 等）→ v0.9.0 的 Capture19 EditMode 字面值（例如 V9-A06「比分 24／24」、V9-A07「36／50」）幾乎全部要重算，而且重寫期間沒有舊條文可以對照。**➡️ 建議答案：新增規則集、保留夾具。**
- **Q2 聖所看「站在板塊上」還是「站在光圈內」？**（E2）板塊（內切半徑 3.79m）比光圈（2.5m）大，守家時比較寬鬆，也符合 GDD「母板塊提供減傷」。**➡️ 建議答案：板塊。**
