## 3. 實作順序與每步驗收

順序 `A → B → C → D`，每步一個可審查的提交（同 v0.8.0，四步共用組裝根與場景，不並行寫檔）。開工前保存 `git status --short --branch` 與 `git rev-parse HEAD` 的輸出。任一步沒過，就回到該步的起點修，不在壞掉的基線上疊下一步。

**所有 V9 條文共同遵守**（承接 v0.8.0 §3，加上 §6 的教訓）：
- 期望值一律寫成字面值，**不得讀 `CaptureTuning`／`CaptureBoardSpec`／`HexBoardLayout` 的欄位**來算期望值。
- 純邏輯時序一律用 dt＝0.25。
- 「沒發生／相等」這類斷言都要附活性證據。
- 每條新測試都要先證明「錯誤實作會讓它紅」：純邏輯由 `mutation_check.py` 證明；Unity 測試由實作者把關鍵行改壞跑一次紅，寫進回報（附紅在哪個斷言），並用**改壞前的備份**還原（不用反向 sed）。
- PlayMode 一律固定 `Time.captureDeltaTime = 1/60`，而且放在 try/finally 或 TearDown 還原（v0.8.0 V4c 的教訓）；窗口幀數寫死，**不得拉長 timeout、加 retry、加 sleep**。
- **時序條件先問「受測動作本身會不會重置計時」**：傳送進光圈＝從 0 開始引導；`ResetForDuel`＝倍率歸 1；`SeedScoresForTest`／`SeedOwnershipForTest` 不動計分時鐘、引導與狂怒。條文中的 f0 一律定義在「受測動作之後」。
- 點擊前先斷言投影離畫面四邊都 ≥ 16px；不成立就判紅，**不得換點**（v0.8.0 V-B05 的教訓）。
- 不得用 `GC.GetAllocatedBytesForCurrentThread` 當 Unity 端證據；Unity 端只用 `ProfilerRecorder`。

**指令**（`<U>`、`<P>`、`<T>` 同 v0.8.0 §3，前綴改為 `v090-`）：`verify.sh` → 場景有改時建場景 → EditMode → PlayMode（依序）；突變只在獨立 worktree 跑，不得與 Unity batchmode 同時使用同一個目錄。
